# Practice-to-WordPress mapping

The [Authoritative Blog Article Distribution workbook](https://docs.google.com/spreadsheets/d/1M0arM4jnZzalySGUKq60Hp1yhTDz2RQTXqMeOWfaOUA/edit) is the editable source for location and WordPress-site assignments. Join `Locations.Code` to `Wordpress Sites.Codes`, and join each doctor's `Doctor Census.Primary Location` by its code in parentheses. The public URL in `Locations.URL` is **not** a WordPress API address.

As of September 23, 2026, the workbook had 58 eligible general-dentist locations with complete, matching public-site and WordPress-site rows. They map to 49 distinct WordPress editing subsites. `CO-08` through `CO-12` share `/co-08/`; `CTX-05` through `CTX-08` share `/ctx-05/`; and `HOU-05` through `HOU-07` share `/hou-05/`. This sharing is retained from the workbook, not inferred from a public website domain. Specialty codes, test/support locations, and the not-yet-launched `DFW-24` and `DFW-25` are excluded.

The initial [BigQuery mapping sync](../sql/initial-practice-site-mapping-2026-09-23.sql) staged those 58 rows in `apex-marketing-n8n.automated_article_creation.practices`. IDs are deterministic (`AZ-01` → `practice_az_01`). Each row has the public URL in `website_domain` and a JSON `publisher_config_reference` containing `location_code`, `wordpress_base_url`, and `mapping_status: "UNVERIFIED"`. Every staged row has `active = FALSE`, `publisher_type = NULL`, and **no credential name**. A fresh query after the sync returned 58 mapped rows, zero active rows, zero publishing-configured rows, and 49 distinct WordPress bases. The existing TEST001 practice was not changed. No doctors, campaigns, invitations, or articles were created by this sync.

The SQL file is a dated initial snapshot, not a replacement for the workbook or a safe script to rerun after the workbook changes. The protected roster preview reads the workbook directly, but new or changed rows are **not yet automatically synced** into BigQuery practice profiles. Reconcile the current workbook, verify additions and removals, then run a reviewed mapping sync before enabling a practice. Never copy a public static URL into `wordpress_base_url` or place a password/application password in the sheet or repository.

Before a real location is enabled, verify that the intended `wordpress_base_url` serves the correct WordPress multisite subsite; confirm the `Apex Article Publisher` account can create/edit posts on that subsite; attach an appropriate credential in n8n; verify any shared-site location routing and article variables; and test one controlled post. Only then set the practice's `publisher_type`, credential reference, and `active` flag through a reviewed change. The publishing workflow still has an independent TEST001-only guard. Real-doctor campaign launch remains disabled, and the Headless Hostman static-site release remains manual.
